What it actually does

Several AI agents that check each other's work

When one AI works on a task alone, it can forget earlier decisions and skip checks. Here the work is split between several AI agents. They check each other, so a mistake that one of them catches never reaches the rest of your project.

👩‍💻

The coder

Writes the code in small, separate steps. No huge change that nobody can read at once.

🔍

The reviewer

Reads every change before it is added to the project. Blocks anything that looks risky or sloppy.

🧪

The QA tester

Keeps a written list of what should work. Marks an item as failing the moment something breaks.

🛠️

The bug fixer

When something breaks, finds the real cause and repairs it. Then adds an automatic check so the same problem cannot come back unnoticed.

📋

The analyst

Reads your request in plain English. Writes a clear description of what should happen and what should not.

🎨

The designer

For features with a screen, plans the layout and how the user moves through it.

That is ai-agent-kit. The system installs 14+ AI agents into your project, together with the rules and automated checks that keep them focused. Each new feature reaches your finished software with fewer mistakes, and you spend less time supervising the AI by hand.
Что это на самом деле

Несколько ИИ-агентов, которые проверяют работу друг друга

Когда один ИИ работает над задачей в одиночку, он может забыть прежние решения и пропустить проверки. Здесь работа разделена между несколькими ИИ-агентами. Они проверяют друг друга, поэтому ошибку, которую заметил один из них, остальные части проекта уже не увидят.

👩‍💻

Программист

Пишет код небольшими отдельными шагами. Без огромных изменений, которые невозможно прочитать за один раз.

🔍

Ревьюер

Перечитывает каждое изменение перед тем, как оно попадёт в проект. Останавливает всё, что выглядит рискованно или небрежно.

🧪

Тестировщик

Ведёт список того, что должно работать. Помечает пункт как упавший, как только что-то ломается.

🛠️

Баг-фиксер

Когда что-то ломается, ищет настоящую причину и чинит. Затем добавляет автоматическую проверку, чтобы та же проблема не вернулась незамеченной.

📋

Аналитик

Читает ваш запрос на обычном языке. Пишет понятное описание того, что должно происходить и чего быть не должно.

🎨

Дизайнер

Для функций с экраном продумывает, как он выглядит и как пользователь по нему перемещается.

Это и есть ai-agent-kit. Система устанавливает в ваш проект 14+ ИИ-агентов вместе с правилами работы и автоматическими проверками, которые держат их в фокусе. Каждая новая функция доходит до готового приложения с меньшим количеством ошибок, а вам нужно меньше времени на ручную проверку за ИИ.
Why several agents, not one?

Six problems several agents solve that one cannot

One AI assistant is fine for short tasks. But for anything serious you need a clear written description, an independent recheck of every change, automatic tests, and a way to pick the work back up after a chat restart. The agents in this kit cover what a single chat cannot.

I have an idea but I do not write code
Describe what you want in plain English. The agents take the request from there: they write the code, recheck it, and run the automatic tests without you steering each step. You confirm the result at the end.
My AI keeps losing context
A single chat forgets older decisions and contradicts itself. Here every step writes its result to a file. The next agent reads the file, not the chat history, so the work continues correctly even if the chat is restarted.
No one reads the code my AI writes
When an AI works alone, nobody reads the code it produces. Here every change is read by a separate AI before it is added to the project. Anything risky is sent back for a fix. No large change is added in one go.
Bugs surface later, not when they are introduced
The project keeps a single file that lists every check it must pass, with the current status of each one. When something stops working, mark its line as failed and run one command. The agents find the cause, repair it, and confirm that the check passes again. You do not have to step through it yourself.
I want a clear process, not chaos
Each command runs a fixed sequence of steps, with an automatic check at the end of each step. You can see at any point which agent is working, what it has produced, and why a step is blocked, instead of a wall of text from one AI you have to read through.
I am afraid the AI will quietly break things
Every change is saved as a separate, reversible step in your project's history. A different AI reads it before it is added. The list of automatic checks catches anything else that breaks. If something still slips through, you can return the project to any earlier point in a few seconds.
Зачем несколько агентов, а не один ИИ?

Шесть проблем, которые решают несколько агентов

Один ИИ-ассистент хорош для быстрых задач. Но для серьёзной работы нужно больше: понятное письменное описание задачи, независимая проверка каждого изменения, автоматические тесты и возможность продолжить работу после перезапуска чата. Эти ИИ-агенты делают то, чего один чат не может.

У меня есть идея, но я не программист
Опишите что хотите обычными словами. Дальше работают агенты: пишут код, перечитывают его и запускают автоматические тесты. Вам не нужно вести их за руку на каждом шаге. Вы только подтверждаете итог.
ИИ постоянно теряет контекст
Обычный чат забывает старые решения и противоречит сам себе. Здесь каждый шаг записывает результат в файл. Следующий агент читает файл, а не историю чата, поэтому работа продолжается правильно даже после перезапуска чата.
Никто не читает код, который написал ИИ
Когда ИИ работает в одиночку, никто не читает код, который он написал. Здесь каждое изменение читает отдельный ИИ перед тем, как оно попадёт в проект. Всё рискованное отправляется на исправление. Никаких больших изменений одной волной.
Баги всплывают потом, а не в момент появления
В проекте есть один файл со списком всех проверок и текущим статусом каждой. Когда что-то перестаёт работать, отмечаете строку как упавшую и запускаете одну команду. Агенты находят причину, чинят её и подтверждают, что проверка снова проходит. Вам не нужно сидеть и смотреть.
Хочется понятного процесса, а не хаоса
Каждая команда запускает фиксированную последовательность шагов с автоматической проверкой в конце каждого шага. В любой момент видно, какой агент работает, что он сделал и почему какой-то шаг заблокирован. Вместо стены текста от одного ИИ, в которой надо разбираться, у вас упорядоченный вывод понятного процесса.
Боюсь, что ИИ потихоньку всё сломает
Каждое изменение сохраняется как отдельный обратимый шаг в истории проекта. Другой ИИ перечитывает его перед добавлением. Список автоматических проверок ловит всё, что всё-таки сломалось. Если что-то проскочило, за несколько секунд можно вернуть проект к любой более ранней точке.

Step by step

Six user scenarios for the Product Owner

Six moments where you, as the PO, step in. Three are kept open so you can read them now. The rest collapse like an FAQ — skim the headlines, expand when you need them. The pattern follows what the 2026 reports from Anthropic, Cursor and OpenAI all agree on: plan first, watch on the loop, review at gates.

Пошагово

Шесть сценариев работы для Product Owner

Шесть точек, где вы как PO лезете в процесс руками. Первые три раскрыты, читайте сразу. Остальные сложены в FAQ. Скользите по заголовкам, открываете нужное. Идея простая. Сначала план, потом код. По ходу работы вы не сидите над каждой строкой, а ловите аномалии. На выходе кит сам себя проверяет по списку из семи пунктов.

What happens, step by step Дальше всё идёт по шагам
  1. You type one line. Stay at the user-value layer ("login via Google"), not the implementation layer ("add OAuth2Client"). Naming files is not your job at this step.
  2. @Main asks four clarifying questions in a single message: which module, what the user needs (1–3 sentences), is UI involved, any constraints (perf / security / compatibility). Answer all four together — every "I don't know" wastes a round.
  3. @Analyst expands your answer into feature.md with sections Why · ACs · Edge Cases · How it works · Test plan. If anything is still ambiguous, it surfaces an Open Questions list. Up to two clarification cycles, then it stops.
  4. @TestKeeper GENERATE turns the Test plan into test-cases.md — every promise gets at least one TC.
  5. CONFIRM. Main shows you the AC count, the Critical EC count, the size of the implementation plan, and any open questions. You type /kit-approve — or set auto_approve: true in the manifest to skip this gate.
Pitfalls to avoid
  • Dictating function names, classes or files at this step. The Plan phase will do that — overspecifying now collapses the agent's design space.
  • Stacking five features into one trigger. Split them. One feature.md per feature, always.
  • Skipping the four questions. They are the cheapest part of the whole pipeline.
  1. Пишете одну строку. На уровне пользователя: «логин через Google». Не на уровне кода: не «добавить класс OAuth2Client». Имена файлов сейчас не ваша забота.
  2. @Main задаёт четыре уточняющих вопроса одним сообщением: какой модуль, что нужно пользователю в одном-трёх предложениях, есть ли UI, есть ли ограничения по перфу, безопасности или совместимости. Отвечайте на все четыре сразу. Каждое «не знаю» это лишний круг.
  3. @Analyst разворачивает ваш ответ в feature.md. Внутри пять секций: Why, ACs, Edge Cases, How it works, Test plan. Если что-то осталось мутным, добавит список Open Questions. Двух циклов уточнений ему хватает, после он сам останавливается.
  4. @TestKeeper GENERATE раскладывает Test plan по test-cases.md. Каждое обещание получает минимум один тест.
  5. Стадия CONFIRM. Main показывает: сколько AC, сколько Critical EC, сколько шагов в плане, какие вопросы открыты. Вы пишете /kit-approve. Или ставите в манифесте auto_approve: true и эти ворота пропускаются навсегда.

Грабли, на которые лучше не наступать. Не диктуйте имена функций и классов на этом шаге. Этим займётся фаза Plan, и если перетянуть руль на себя сейчас, агенту негде будет думать. Не складывайте пять фич в один триггер: один feature.md равно одна фича, без вариантов. И не пропускайте четыре вопроса от Main. Это самая дешёвая часть всего процесса.

Stop signals — read immediately if you see these in a checkpoint

  • CIRCUIT BREAKER: — an agent self-stopped to avoid a loop. Do not just retry — read why.

The big idea. Production-readiness is not a vibe. It's a binary gate of seven checks, enforced by @DoDGate, plus a five-minute manual pass from you. The kit cannot CLOSE the task until both the machine gate and you give green. Готовность к проду это не «по ощущениям». Это бинарные ворота из семи проверок, и держит их @DoDGate. The seven machine checks (run by @DoDGate) Семь автоматических проверок от @DoDGate
  • AC coverage. Every Acceptance Criterion has at least one passing TC.
  • Edge case coverage. Every Critical edge case has a passing TC.
  • Test status. test-cases.md has no FAIL or PEND row in scope.
  • Reviewer verdict. The last @Reviewer pass returned CLEAN — no open CRITICAL or HIGH findings.
  • Build green. Compile and lint passed on the latest run.
  • Traceability matrix. No orphans in the chain AC / EC → TC → test file → source symbol.

Your five-minute human pass on top
  1. Run the app yourself. Walk one happy path and one Critical edge case from the AC list. Five minutes. No exceptions, even when the gate is green — the gate proves consistency, not user fit.
  2. UI features: open the dev server, eyeball light + dark mode, one mobile width, one keyboard-only navigation pass.
  3. Security-surface features (auth, payments, file upload, deserialization, RBAC): confirm the @Reviewer pass ran with TOUCHES_SECURITY_SURFACE=true. If not, ask Main to re-dispatch @Reviewer with that flag.

4. Push back when the AI heads the wrong way — give the agent feedback mid-flight 4. Сказать ИИ, что он свернул не туда. Обратная связь по ходу работы

Three places to interject, depending on the phase.

  1. Before CONFIRM (CLASSIFY / ANALYSIS): just answer in the chat. Main routes you back to @Analyst, who patches feature.md.
  2. At CONFIRM: don't approve. Type the change you want — "Drop AC-3, it's out of scope" or "EC-2 should fail closed, not open". Main re-runs the affected step.
  3. Mid-EXECUTE: the loudest path. Hit Esc to interrupt the AI, then state what's wrong in one precise sentence. Stop > redirect. Cursor's official agent guide and Anthropic's 2026 report both call this out as the #1 productivity move.

Faster than the chat: edit the source-of-truth file directly.

  • Add an AC or EC by editing feature.md. The next pass picks it up.
  • Add a TC by editing test-cases.md. /kit-fix TC-NN then targets it.
  • Force a re-plan by editing the Implementation plan section and clearing the [x] marks for the affected steps.
Things that look like feedback but aren't
  • "Ignore my last instruction." The agents log everything; ambiguity stays in the trail. Edit the artefact instead.
  • Accumulating five complaints into one paragraph at the end of the run. One precise objection now beats five vague ones at the end.
  • "Make it better." The agent has no model of "better." Name the AC, the EC, the TC, or the file.

Три точки, где можно вмешаться. Зависит от того, в какой фазе кит сейчас.

  1. До CONFIRM (это фазы CLASSIFY и ANALYSIS): просто отвечаете в чате. Main кидает запрос обратно к @Analyst, тот правит feature.md.
  2. На CONFIRM: не аппрувьте. Напишите, что хотите поменять: «убрать AC-3, он вне скоупа» или «EC-2 должен fail closed, а не open». Main перезапустит нужный шаг.
  3. В середине EXECUTE: самый громкий путь. Esc, чтобы прервать ИИ, и одной точной фразой говорите, что не так. Сначала остановили, потом перенаправили. Cursor в гайде по агентам и Anthropic в отчёте 2026 года называют это движением номер один по приросту продуктивности.

Быстрее чата: правьте source-of-truth файл напрямую.

  • Открыть feature.md и руками добавить AC или EC. Следующий проход подхватит.
  • Открыть test-cases.md и добавить строку TC. /kit-fix TC-NN потом возьмёт её в работу.
  • Заставить кит перепланировать: открыть Implementation plan, снять [x] с тех шагов, которые надо переделать.

Что выглядит как фидбек, но им не является. «Игнорируй моё прошлое сообщение»: агенты логируют всё, двусмысленность остаётся в следе. Лучше отредактируйте артефакт. Копить пять претензий в один абзац в конце прогона: одно точное возражение прямо сейчас лучше пяти размытых потом. И «сделай лучше»: у агента нет модели «лучше». Назовите AC, EC, TC или конкретный файл.

5. Test the result and feed back what's wrong — what to look at, what to run, how to report 5. Протестировать результат и сообщить, что не так. Что смотреть, что запускать, как репортить

Where to look — three layers.

  1. Status layer. test-cases.md — every TC the kit knows about. Anything not PASS is open work. Sort by status; FAIL rises to the top.
  2. Trace layer. The full failure trace is in .planning/tasks/<slug>.md under the latest @TestKeeper EXECUTE checkpoint. Stack traces, command output, exit codes.
  3. Diff layer. git diff main..HEAD on the feature branch. Read it like a code review; the kit already did one pass, your pass catches different things.

What to test — in this order.

  • Golden path from the AC list — five minutes, manual. The single most important pass.
  • Critical edge cases from feature.md § Edge Cases — the rows tagged Critical. Skip the LOW/MEDIUM ones unless the feature is high-risk.
  • Regressions — anything next to your change. Re-run the existing test suite (the same one @TestKeeper already ran is fine).
  • Security & perf — only for features that touch external surface or have explicit perf ACs.

How to feed back.

  • Bug maps to an existing TC: /kit-fix TC-NN. Straight into the BUG pipeline, no overhead.
  • Bug is new: /kit-fix "describe the bug in one line". The kit creates the TC first, then starts the fix.
  • Issue is "the design is wrong, not the code": don't /kit-fix. Reopen the feature — edit feature.md, then re-trigger an EXECUTE step. Fixing a design decision in BUG mode produces patches on patches.
Honest signal vs. cheap signal "Looks fine to me" is not test feedback. Either run the path or say you didn't. Cheap green confirmations are the single biggest cause of "passed in dev, broke in prod."

Куда смотреть. Три уровня.

  1. Уровень статуса. test-cases.md, в нём все TC, о которых знает кит. Всё, что не PASS, это открытая работа. Отсортируйте по статусу, FAIL уйдёт наверх.
  2. Уровень трассы. Полная трасса падения лежит в .planning/tasks/<slug>.md под последним чекпоинтом @TestKeeper EXECUTE. Стактрейс, вывод команд, exit codes.
  3. Уровень diff. git diff main..HEAD по фиче-бранчу. Читайте как код-ревью. Кит уже сделал один проход, ваш ловит другое.

Что тестировать и в каком порядке.

  • Golden path по списку AC. Пять минут вручную. Самый важный единичный проход.
  • Critical edge cases из feature.md, секция Edge Cases. Берёте только Critical. LOW и MEDIUM пропускаете, если фича не из категории высокого риска.
  • Регрессии. Всё, что рядом с вашим изменением. Прогоняете существующий тест-сьют. Тот же, что уже гонял @TestKeeper, сойдёт.
  • Безопасность и перформанс. Только для фич, которые выходят на внешнюю поверхность или имеют явные perf-AC.

Как давать фидбек.

  • Баг ложится на существующий TC: /kit-fix TC-NN. Сразу в BUG-пайплайн, без накладных.
  • Баг новый: /kit-fix "описание бага одной строкой". Кит сначала создаст TC, потом начнёт фикс.
  • Проблема в дизайне, а не в коде: не используйте /kit-fix. Откройте фичу заново, отредактируйте feature.md и перезапустите шаг EXECUTE. Если чинить дизайн через BUG-режим, получаете заплаты на заплатах.

Честный сигнал против дешёвого. «Вроде нормально» это не тест, а отписка. Либо реально пройдите путь, либо честно скажите, что не проходили. Дешёвые «зелёные» подтверждения это главная причина, почему фича работала в dev и упала в prod.

6. Drive a defect through the bug pipeline — from /kit-fix to a regression test 6. Провести дефект по процессу багфикса. От /kit-fix до регрессионного теста

Three entry shapes — pick one.

  • /kit-fix alone → @TestKeeper SCAN lists every FAIL / PEND TC; you pick which to fix.
  • /kit-fix TC-07 → straight to TRIAGE for that TC.
  • /kit-fix "login crashes on emoji" → @TestKeeper APPEND creates a new TC, then TRIAGE.

Pipeline shape.

INTAKE → TRIAGE → (DEBUG if unclear) → FIX → RE-VERIFY → CHECKPOINT → HAND-OFF → RETRO (CRITICAL/HIGH only)

Where you step in.

  1. TRIAGE. The kit may ask: "stacktrace or repro?" Provide both, in one reply. Missing stacktrace = guaranteed extra round.
  2. DEBUG (only for hard bugs). @BugFixer runs read-only and produces a failing test that pins the bug. You don't need to do anything yet.
  3. FIX. @BugFixer fixes the root cause (not the symptom) and adds a regression test, so the same defect cannot return unnoticed. @Reviewer reads the diff. Build runs.
  4. RE-VERIFY. The kit re-runs the TC and asks you to confirm PASS. Confirm honestly — see the previous scenario about cheap green signals.
  5. RETRO (CRITICAL / HIGH only). The bug-retro skill writes either a new regression test or a guideline update. Read it — that's where the kit gets smarter for next time.
When the kit stops on its own
  • 3rd RERUN failure — same TC fails three times in a row. Kit escalates with the full retry chain. Decide: revert, hand off to a human, or change the TC's expected behaviour.
  • Same compile error after two fixes — circuit breaker. The fix direction is wrong; do not retry the same approach.
  • 3rd review-fix cycle — Reviewer keeps finding CRITICAL on the same area. Probably the design conflicts with the rules; reopen the feature instead.
The Defects log is your audit trail Every defect goes OPEN → FIXED → VERF (you confirm). The lifecycle lives inside test-cases.md next to the TC. Don't delete entries; "wont-fix" with a Notes line is the right closure when the bug isn't worth fixing.

Три формы входа, выбираете одну.

  • /kit-fix без аргумента: @TestKeeper SCAN перечисляет все FAIL и PEND TC, вы выбираете, что фиксить.
  • /kit-fix TC-07: сразу в TRIAGE по этому TC.
  • /kit-fix "логин падает на эмодзи": @TestKeeper APPEND создаёт новый TC, потом TRIAGE.

Форма пайплайна:

INTAKE → TRIAGE → (DEBUG если неясно) → FIX → RE-VERIFY → CHECKPOINT → HAND-OFF → RETRO (только для CRITICAL и HIGH)

Где вы вступаете.

  1. TRIAGE. Кит спросит: «стактрейс или repro?». Дайте оба сразу одним ответом. Если стактрейса нет, гарантированно лишний круг.
  2. DEBUG (только для трудных багов). @BugFixer работает в read-only и пишет падающий тест, который фиксирует баг. Вам пока ничего делать не нужно.
  3. FIX. @BugFixer чинит первопричину, а не симптом, и добавляет регрессионный тест. Чтобы тот же дефект не вернулся незамеченным. @Reviewer читает diff. Идёт билд.
  4. RE-VERIFY. Кит перезапускает TC и просит вас подтвердить PASS. Подтверждайте честно. Про дешёвые «зелёные» сигналы выше уже было.
  5. RETRO (только CRITICAL и HIGH). Скилл bug-retro пишет либо новый регрессионный тест, либо обновление гайдлайнов. Прочитайте. Так кит становится умнее на следующий раз.

Где кит сам останавливается. Третий RERUN с фейлом: один и тот же TC падает три раза подряд, кит эскалирует с полной цепочкой попыток. Дальше уже вам решать: откатывать, передавать человеку или менять ожидаемое поведение TC. Одна и та же compile-ошибка после двух фиксов: circuit breaker. Направление фикса неверное, тот же подход повторять бесполезно. Третий цикл review-fix: Reviewer продолжает находить CRITICAL в одном месте. Скорее всего дизайн конфликтует с правилами, открывайте фичу заново, точечными правками тут не выехать.

Defects log это ваш аудит-след. Каждый дефект идёт по статусам OPEN, FIXED, VERF (это уже подтверждаете вы). Жизненный цикл лежит внутри test-cases.md рядом с TC. Записи не удаляйте: «wont-fix» с пометкой в Notes это нормальное закрытие, если баг чинить не стоит.

Building blocks of your setup

Build your setup from profiles

A profile is one building block of your setup. Each profile records one fact about your project: "I am using Kotlin," "I am building a Compose app," "I will run inside Claude Code," "Add the basic security rules."

kotlin-gradle + compose-multiplatform + claude-code + security-baseline = your project setup

You pick a few during install. The kit assembles them into your project. Need SOLID design principles later? Add the solid profile. Language, framework, and AI assistant stay untouched. Want to switch from Claude Code to OpenCode? Replace only the AI-assistant profile.

The five categories of profiles

Every profile belongs to one of these five categories. Each category answers a different question about your project. Profiles in different categories never get in each other's way.

The profile names look technical, but you do not need to remember them. The install asks plain questions like "Which programming language?" or "Which AI assistant?" and picks the right profiles for you.

FAQ

Common questions

If you have never used a kit of AI agents before, these are probably the questions on your mind.

Do I need to know how to code?

Not really, but it helps. The kit handles the engineering side: coding, rechecking, and testing. You need to be able to:

• describe what you want clearly,
• run commands in a terminal,
• check whether the result matches your idea.

If you have ever written clear instructions for a freelancer, you already have the skill.

How much does this cost?

The kit itself is free and open source. The cost is the AI assistant you use it with (typically Claude Code, OpenCode, or Cursor), plus the cost of the model API calls behind it.

Expect a few dollars per significant feature, depending on how much code is involved. There are no kit-specific fees.

What if the AI makes a mistake?

The whole point of having several agents is that a mistake made by one of them is caught by another. A separate agent reads every change before it is added to the project. Another agent keeps a list of automatic checks that switch to FAIL the moment something stops working.

Every change is also saved as a separate, reversible step in your project's history. You can always return to any earlier point.

Where does my code live? Is it private?

On your machine, inside your project's git repository, just as if you had written it yourself.

The kit does not upload code anywhere. The AI assistant you have chosen sends pieces of code to its own provider while you work. That is the same trade-off as using any AI coding tool.

Is it safe to use on real projects?

Yes, with normal precautions:

• never paste API keys into the settings file (the install rejects them automatically),
• commit your work to git regularly,
• read meaningful changes before they are added to the project.

The rules are the same as for any AI coding assistant. Having several agents only makes the safety net wider, not weaker.

Which AI assistant should I pick: Claude Code or OpenCode?

Claude Code: easiest setup, best Claude models, polished experience.

OpenCode: more flexible. Pluggable model providers and a more open architecture.

You can also install both side by side and switch between them. The agents are identical on both.

What if I get stuck partway through a workflow?

Run /kit-status. It tells you which step is active, what is blocking it, and what comes next. Run /kit-resume to continue exactly where you left off, even after closing your AI assistant.

Every step writes a checkpoint to .planning/tasks/<slug>.md automatically — there is no manual checkpoint command, and no "lost progress" between sessions.

Can I change an agent's behaviour?

Yes. Each agent is just a markdown file in .claude/agents/ or .opencode/agents/. Open it, edit the instructions, save. The next run uses the new instructions.

For deeper changes, add or modify a capability profile, then run /kit-update to refresh everything cleanly.

FAQ

Частые вопросы

Если вы раньше не работали с набором ИИ-агентов, скорее всего, у вас в голове крутятся именно эти вопросы.

Нужно ли уметь программировать?

Не обязательно, но полезно. Набор сам занимается инженерной частью: кодом, перечитываниями и тестами. От вас требуется уметь:

• чётко описать, чего вы хотите,
• запускать команды в терминале,
• проверять, соответствует ли результат вашей задумке.

Если вы когда-нибудь писали понятные инструкции фрилансеру, нужный навык у вас уже есть.

Сколько это стоит?

Сам набор бесплатный и с открытым кодом. Платите вы за ИИ-ассистент, который его запускает (обычно это Claude Code, OpenCode или Cursor), плюс за вызовы API моделей.

На серьёзную функцию обычно уходит несколько долларов, в зависимости от объёма кода. Дополнительных платежей именно за набор нет.

А что, если ИИ ошибётся?

Смысл нескольких агентов в том, что ошибки одного из них ловит другой. Отдельный агент перечитывает каждое изменение перед тем, как оно попадёт в проект. Ещё один ведёт список автоматических проверок, которые переключаются в FAIL, как только что-то перестаёт работать.

Каждое изменение к тому же сохраняется как отдельный обратимый шаг в истории проекта. Всегда можно вернуться к любой более ранней точке.

Где хранится мой код? Это приватно?

На вашем компьютере, внутри git-репозитория проекта. Точно так же, как если бы вы писали его сами.

Набор ничего никуда не загружает. ИИ-ассистент, который вы выбрали, отправляет фрагменты кода своему провайдеру во время работы. Это тот же компромисс, что и при использовании любого ИИ-инструмента для написания кода.

Можно ли использовать на реальных проектах?

Да, с обычными мерами осторожности:

• не вставляйте API-ключи в файл настроек (установка отбрасывает их автоматически),
• регулярно коммитьте работу в git,
• перечитывайте значимые изменения до того, как они попадут в проект.

Правила те же, что и для любого ИИ-ассистента по коду. Несколько агентов лишь делают страховочную сетку шире, а не уже.

Какой ИИ-ассистент выбрать: Claude Code или OpenCode?

Claude Code: самая простая установка, лучшие модели Claude, отполированный UX.

OpenCode: больше гибкости. Подключаемые провайдеры моделей и более открытая архитектура.

Можно установить оба параллельно и переключаться между ними. Агенты в обоих одинаковые.

А если я застряну посреди процесса?

Запустите /kit-status. Команда покажет, какой шаг сейчас активен, что его блокирует и что будет дальше. /kit-resume продолжает ровно с той точки, где вы остановились, даже после закрытия ИИ-ассистента.

Чекпоинт пишется в .planning/tasks/<slug>.md автоматически после каждого шага — отдельной команды нет, и «потерянного прогресса» между сессиями не бывает.

Можно ли поменять поведение агента под себя?

Да. Каждый агент — это просто markdown-файл в .claude/agents/ или .opencode/agents/. Открываете, редактируете инструкции, сохраняете. Следующий запуск использует новые инструкции.

Для более глубоких изменений добавьте или измените capability-профиль, затем запустите /kit-update для чистого обновления.
